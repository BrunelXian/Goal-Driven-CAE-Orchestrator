# MCP Registration & Runtime Verification

适用于新增、重新注册、重建或修改MCP Server后的环境预检，以及既有连接的发现/调用故障。
这是三个Skill的静态流程协议，不新增Runtime、状态服务、MCP代理或自动重启脚本。

## 当前Desktop Main的验收

分别记录MCP Registration、Runtime Discovery、实际调用与身份核验的证据、来源和未验证项。
`codex mcp list`、`codex mcp get`、配置文件存在或独立CLI/SDK测试成功只证明各自观察范围，
不能代替当前科研项目原Desktop Main的工具发现与真实调用。其他会话的成功也不代替当前Main。
Setup在其他对话执行时，只交付诊断和待核验项，由原Main实际调用；不得代Main宣称通过。

当前Main先识别正确项目/绝对路径、服务器别名及宿主实际暴露的工具目录，再使用已授权、
无副作用的只读接口取得实际回包。不能调用提交、ODB提取、Grant或预算变更来测试连通性。
没有安全只读入口或调用授权时保留BLOCKED/NOT_VERIFIED；不以危险探针补齐。
保留真实调用线程/轮次/工具引用、精确参数和必要的原始响应；避免记录凭据和敏感环境变量。

核对服务器来源/身份、版本、工具目录和允许的权限范围，以及实际响应的错误与身份字段。
按该服务器的正式契约检查 `isError`、业务成功字段、项目/实例及约定的计划/摘要等绑定；
同时返回文本JSON与structuredContent时核对二者一致。不能把通用成功字段或版本号单独当作可信来源。
字段未暴露就写NOT_VERIFIED，不编造进程、源码或版本身份。目录/权限与预期不符也停止依赖工作。

## 三条处理路径

| 路径 | 实际观测 | 处理与恢复条件 |
|---|---|---|
| 正常连接 | 当前Main发现目标工具，安全只读调用成功且身份/版本/权限/回包核验通过 | 不要求重启；记录本轮已验证范围，才允许恢复受该MCP阻断的工作。 |
| 发现失败 | 注册证据通过，但当前Main未发现目标服务器/工具 | Runtime Discovery: BLOCKED；检查配置加载、项目环境和会话状态。CLI成功不能消除阻断。 |
| 重启恢复 | 发现失败后需要刷新Desktop，Main已保存检查点，用户回到原Main发送Resume | 先恢复原状态，再重新发现并实际调用、核对身份/版本/目录/权限/回包；复验通过才READY_TO_RESUME，否则继续BLOCKED。 |

注册已通过但Runtime Discovery失败时，先检查实际使用的配置作用域/加载来源、工作目录、
项目Trust、服务器是否启用、允许工具配置、当前Main会话与运行环境状态及可用诊断。
无法观测已加载配置就说明UNKNOWN，不凭CLI解析结果猜测Desktop已加载。
配置修复仍遵守现有授权，不借诊断擅自改用户配置；不要求研究者自行诊断内部MCP配置。
宿主有可用且获准的连接重载方式时可以先尝试并复验。无可用重载方式或重载后仍发现失败，
需要刷新进程环境时，保存检查点并提示用户完全退出/重启Desktop。
不是每次MCP重建都必须重启Desktop；发现与调用已经通过时不安排重启。
发现成功但调用失败或身份不符也继续阻断，保留原始错误，按具体原因诊断，不能以重启保证通过。

## Main保存，Setup不写科研状态

Setup只读核验、交付实际诊断和最小人工操作。Conduct中的Main是科研主状态唯一写者：

- 保存当前Research Card及六模块中的实际进展，Task Cards中的未完成任务/允许范围和输入引用，
  真实项目路径、原Main及已有角色Thread ID/宿主引用（未暴露为NOT_EXPOSED）。不重建既有Agent。
- 在已有Handoff/后续追加研究日志中保存恢复入口、当前阶段/模型版本、环境阻断原因、
  已完成和未完成/结果未知任务、最后实际回包及下一步复验步骤，指向真实当前文件。
  更新受影响文件的引用和实际摘要；不回改原报告、历史日志或验收证据，不新增Schema字段。
- 尚无Research Card等文件时不伪造“已保存”；只在授权范围保存现有真实记录并说明缺项，
  不为了环境恢复重新立项。检查点写入失败/引用不完整时不得标Research State: Preserved。
- 确认其他运行任务已安全停止，不能确认时请用户先确认；不自动终止任务、退出Desktop或
  盲目重发接受/完成状态未知的请求。不为了刷新环境创建Grant或做Solver/ODB操作。

遵循既有Research Card视觉规范：保留六模块和YAML Schema，在❺ Research Roadmap保留未完成项，
在❻ Next Action与工作回复中给出恢复动作。提示是环境状态，不改变科研phase、模型资格或执行结论。

## MCP Environment Refresh Required

仅在注册实际通过、当前Main发现阻断且研究记录保存核对完成后，向用户显示以下简短提示。
状态不满足时按实际状态报告，不能套用PASS或Preserved。完整退出前仍须确认其他运行任务安全停止。

> **MCP Environment Refresh Required**
>
> - MCP Registration: PASS
> - Runtime Discovery: BLOCKED
> - Research State: Preserved
>
> 请在确认其他运行任务安全停止后，完全退出并重新启动 Codex Desktop，返回当前科研项目的原 Main 会话，并发送 Resume。
>
> VeriCAE 将重新验证 MCP 连接，并恢复未完成的研究流程。

## Resume与恢复范围

用户重启后回到原项目的原Main继续，不无故重建角色或丢弃已有研究状态。先打开恢复入口，
读取当前Card、Task Cards、模型定义和最新日志，核对项目/线程绑定、实际文件内容与引用/摘要；
发现未经说明的变更先停止相关工作并报告，不自动覆盖或恢复旧副本。
重启完成、用户发送Resume、CLI成功都不代表连接已通过；按“当前Desktop Main的验收”重新
发现并调用目标MCP，复核身份、版本、工具目录、权限边界及实际回包，再记录本轮证据。
环境验证通过才可解除对应阻断，失败则保持BLOCKED；仅需环境恢复验收时报告READY_TO_RESUME并停止。
后续任务仍按既有任务范围、当前用户指令和可信执行授权推进，不因恢复就自动派发任务或升级权限。
保留原FAILED、REVIEW_REQUIRED、INSUFFICIENT等历史状态；环境成功不改变结果完整性、模型或科研执行资格。

静态协议测试和隔离文件恢复测试只检查规则/文件连续性，不能证明Desktop重启、工具发现或实际调用通过。
