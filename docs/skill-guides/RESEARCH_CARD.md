# CAE Research Card — 科研任务卡规范

**文档日期：**2026-11-20。  
**适用范围：**CAE Agent 的 Initiate CAE Research 与 Conduct CAE Research。  
**视觉基线：**CAE Research Card Design v1.0；保留 2026-11-19 定版的原生 Markdown 结构。  
**文档性质：**面向用户和 Agent 的展示与记录规范；文档发布不代表插件集成、会话创建、模型验证或真实求解已经完成。

Research Card 是研究项目的简明状态视图。它帮助研究者和 Main 快速回答：研究什么、有哪些假设、模型发展到哪里、谁在做什么、目前卡在哪一步，以及接下来应该采取什么行动。

卡片使用正式记录与研究资料生成。实际项目身份、执行状态和验证判定仍须分别核对其来源，具体规则见[工作流与证据规范](RESEARCH_WORKFLOW_AND_EVIDENCE.md)。完整模型定义与资格说明见 [Sanity Model 用户指南](../user/SANITY_MODEL_USER_GUIDE.md)。

## 2. 何时生成与展示

### 2.1 首次规划

在 Initiate 的 Research Planning 阶段，形成初步研究理解后生成完整 Research Card（Draft），作为该阶段的交付成果之一。项目名称尚未确认时，明确它是建议名称。

初始卡片可以包含待确认的物理条件、尚未建立的模型和拟议分工。六个模块都应出现，缺项如实填写，不为使卡片完整而补造数值、文件、会话或完成状态。

Draft 卡片的出现不意味着已创建 Codex Desktop Project、登记正式 ResearchProject、建立模型或执行计算。卡片文件已经保存，也不等于 Core 已完成正式登记；优先使用“尚未正式登记”等明确表达。

### 2.2 正式研究与恢复

在下列时机更新并按需展示完整卡片：

- 初始化完成并交给 `<ProjectName> Main`。
- 跨对话恢复研究，完成最新状态核对后。
- 研究目标、关键假设、有效模型版本、角色可用性或主要研究路线发生变化。
- 一轮研究形成重要结果、遇到需要用户处理的阻塞，或作出暂停、结束决定。
- 用户要求查看当前研究全貌。

每个可检查工作单元仍须按工作流规范留下科研日志。日常进展可简述变化、证据和下一步，不需要每次工具调用或每条回复重复输出整张卡片。完整卡片的更新应与真实进展一致，不能因减少展示而遗漏状态同步。

卡片中的 Next Action 可以是 Main 在授权范围内继续执行的动作；只有确实缺少用户决定时才写成问题。

## 3. 固定排版结构

### 3.1 渲染方式

使用 Codex 聊天正文中的原生 Markdown。保持可复制、可编辑，不使用 HTML/CSS、独立网页、MCP App 或图片替代卡片。字体、表格边框、圆角与实际颜色由客户端主题控制，不承诺不同客户端的像素级一致性。

向用户展示时直接输出 Markdown 正文，不把整张卡片包在代码块内。本文第 7 节使用代码块仅为方便复制模板。

### 3.2 边界与标题

卡片顶部和底部各放一行完全相同的横线，逐字使用：

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

主标题固定为二级标题：

```markdown
## ⚛️ CAE Agent · Research Workspace
```

下一段为加粗项目名及行内代码状态标签，以全角空格分隔，例如：

```markdown
**Beam-InvOpt**　`Draft 01`　`Planning`
```

`Draft 01`、`Planning` 等是展示标签，不是新建的后端状态枚举。正式阶段应根据实际内容调整；卡片修订号、模型版本和 Core 修订号分别记录，不能互相推定。

六个模块使用三级标题，顺序与字符固定：

1. `### ❶ Research Contract`
2. `### ❷ Research Assumptions`
3. `### ❸ Model Evolution`
4. `### ❹ Research Subagent`
5. `### ❺ Research Roadmap`
6. `### ❻ Next Action`

卡片底部横线之后，用 `### 💬 Codex · 工作回复` 承接正常工作回复。保留标题、段落、表格前后及两个角色表之间的空行；引用块中的空段落也保留 `>`。

## 4. 六个模块的填写要求

### 4.1 ❶ Research Contract

用引用块展示加粗的“研究命题”，下一引用段落说明研究问题与主要目标量。用两个独立段落分别给出 **基准模型** 和 **研究交付**，最后另起一段放三枚行内代码标签，分别概括方案、登记和计算状态。

这里展示 Research Contract 的简明摘要；正式合同的目标、允许探索范围、评价标准、预算与修订关系仍由正式研究记录管理。草案必须标明是草案。

目标量保留必要的数值、单位和观测位置。若来自用户的目标尚含糊，应显示待确认内容，不自行固定默认容差。模型仍是候选时，在“基准模型”段落中直接说明资格待确认。

计算标签应明确所指范围，例如“本轮尚未提交”或“本轮运行中”。已有历史计算的项目不得被概括为“尚未执行计算”。

### 4.2 ❷ Research Assumptions

按以下顺序使用三个独立段落：

- **已提供：**用户资料、已有模型或可核实记录中明确给出的条件。
- **暂定假设：**为规划或探索提出、尚未充分确认的假设。
- **待确认：**会影响模型、执行或结论，需要补充信息或作出决定的事项。

“用户已提供”不等于“已经物理验证”。保留会影响研究解释的假设与不确定性；能够由 Agent 检查解决的事项，应安排检查，不把它们全部改成要求用户填写的表单。

### 4.3 ❸ Model Evolution

使用三列表格：**模型版本 / 相对基准的变化 / 状态**。版本名称加粗，表格下保留斜体说明，解释当前记录是规划、已建立模型、已验证版本还是混合状态。

版本可以是项目已有标识。示例中的 `M0`、`M1`、`M2` 只用于说明，不要求改名既有模型。理论参考可以作为路线中的一项，但必须标明是理论依据，不能冒充实际有限元模型。

分别说明模型存在、通过哪些检查、对什么用途具有资格。资格未定、只完成输入生成或仍在探索时，不标为“验证完成”。新候选不会自动继承原基准所有资格。

完整几何、材料、Step、边界、载荷、Interaction、网格和输出定义保存在 `models/SANITY_MODEL_SPEC.md`。卡片只显示模型摘要与演进；模型定义表首次展示，模型定义或版本变化时再展示，不重复塞进每次卡片。

### 4.4 ❹ Research Subagent

固定使用两张独立双列表格，形成 2×2 角色布局：

- 第一张：🧠 **Main Agent** 与 ⚙️ **CAE Subagent**。
- 第二张：📊 **Results Subagent** 与 🛡️ **Independent Validation**。
- 每张表依次包含角色表头、职责行、状态行；两表之间保留空行。
- 表格后保留斜体说明，明确哪些是拟议角色、哪些已实际建立，以及 Main 是否已确认为项目主对话。

正式研究的三个核心角色是 Main、CAE、Results；Independent Validation 按需增加。可保留它的展示单元并写“按需设置”，不因此创建无任务的会话或暗示独立验证已经存在。其他专业 Subagent 可在表后简述其真实职责与状态，保持两张核心表的结构。

统一使用 `<ProjectName> Main` 与 `<ProjectName> <Role>` 命名。名称和角色描述不证明实际会话存在。新建或重建的专业 Subagent，须经 Main 实际发送消息并收到正确回复，才能标记 `READY`。

`READY` 只表示所声明的通信准备检查通过，不等于该 Agent 已完成任务、具备经过验证的专业能力，或已建立操作系统级权限隔离。恢复时若会话失效或发生变化，先核实再更新状态。

后端登记的逻辑角色或任务步骤不一定对应真实的 Codex 子会话。例如回执中的 `role_mode=LOGICAL_STEP`、`host_attestation=UNATTESTED` 只能按其实际含义展示，不能转换为“子 Agent 已建立”或通信 `READY`。

### 4.5 ❺ Research Roadmap

使用原生 Markdown 任务列表。每项包含阶段编号、状态和简明内容，前两项阶段名称加粗；当前主要检查点用行内代码 `当前检查点` 标注。

`[x]` 仅用于该项所声明成果已经完成且有依据的情形，其余使用 `[ ]`。研究问题已经理解可以完成，但不能因此勾选项目登记、模型资格或真实执行。后台任务已接受、排队和求解完成也应分别判断。

路线根据项目调整，不要求所有项目复用示例阶段或线性执行。新一轮研究可以新增适当的任务或更新未完成项，保留已完成事实与决策轨迹。失败、取消、证据不足或预算耗尽应按实际结果说明，不为了使路线全勾选而改写成功条件。

### 4.6 ❻ Next Action

使用一个独立引用块，突出当前最重要的一项决定或动作，建议句加粗。

- 需要用户决定：说明具体问题、建议选项及其影响，问题另起引用段落。
- 已在授权范围内：说明 Main 将推进的动作及预期得到的结果，不重复请求同一授权。
- 当前受阻：说明缺项和恢复所需动作，不把受阻表述为正在计算。
- 研究结束：说明成果位置或结论复核动作，不自动开启新一轮研究。

下一步可以是读取资料、检查模型、分析已有数据或开展资格试验。它应符合真实任务与授权，不能因卡片生成而自动变成求解请求。

## 5. 状态与证据规则

保留原型的四种状态点：

| 状态点 | 语义 | 使用要求 |
| --- | --- | --- |
| 🟢 | 已完成 | 明确完成的是哪项工作或检查，并有对应依据。 |
| 🔵 | 进行中 | 存在实际进行中的活动，说明活动内容。 |
| 🟡 | 待确认 | 确实需要确认，指出具体事项。 |
| ⚪ | 未开始 | 包括拟议、待分派、按需设置。 |

四种状态点不覆盖全部异常。失败、受阻、取消和原因待诊断，用清楚的文字及实际返回的状态码表达，例如 `受阻 · BACKEND_NOT_IMPLEMENTED`；不要为这些情况虚构后端枚举，也不要用“进行中”掩盖停滞或用绿色表示未执行的检查。

| 卡片中的陈述 | 应核实的来源 |
| --- | --- |
| 项目已登记、任务已持久化、预算或正式状态已改变 | Core 正式接口的实际回执和必要读回。 |
| 模型已经建立、输入已经生成 | 实际模型或输入文件、版本及相关检查记录。 |
| 模型对某用途已取得资格 | 对应模型版本、研究用途和验证证据。 |
| Subagent 已建立、通信 `READY` | 实际会话标识或宿主确认，以及真实消息往返。 |
| 求解已接受、运行或完成 | 对应本次请求的 AbqJobPilot Receipt / Run 与相应工程产物。 |
| 研究目标已经达成 | 既定判据、实际结果和相应独立验证；不能仅依据进程退出或拟合曲线外观。 |

未得到依据的状态保留“待检查”“未验证”或具体未知。Fixture、TEST_ONLY、合成结果和历史数据复核须在卡片或紧邻的工作回复中显著标注，不能让读者误以为是本轮真实求解。

Main 或独立审查 Agent 给出的意见应标为研究建议或审查结论。只有正式验证接口实际返回或读回的判定，才能表述为 Core 已登记的 VerificationRecord；未持久化的评审意见不能代替该记录。

卡片的文字、复选框和色点本身不是回执。用户直接编辑卡片时，变化先作为研究意图或草案处理；需要正式变更的内容仍按工作流登记与核实。

## 6. 保存、版本与跨对话恢复

按已确认的项目布局维护以下资料，优先复用现有文件：

| 项目位置 | 用途 |
| --- | --- |
| `research/RESEARCH_CARD.md` | 最新可读 Research Card。 |
| `research/TASK_CARDS.md` | 任务安排、状态摘要及正式任务引用。 |
| `models/SANITY_MODEL_SPEC.md` | 模型定义表、版本、资格与证据引用。 |
| `docs/initiation/HANDOFF.md` | 初始化交接摘要和资料入口。 |
| `docs/research-runs/` | 按可检查工作单元保存的科研日志。 |

规划尚无正式工作目录时可先在对话生成 Draft；确认目录后保存。不要为了保存一张卡片自行建立正式项目或替代 Core 数据库。

更新卡片时核对最新正式记录与产物，再更新显示标签、路线和下一步。来源不一致时保留差异并说明，不能以旧卡片覆盖新回执，也不能以文件保存成功证明正式状态已写入。

在工作回复、相关任务或科研日志中保留足够的来源引用，使卡片能够关联到正式项目、合同修订、模型版本、执行和验证证据。需要排查时再展开这些标识，首次界面不必堆满内部实现字段。

Handoff 和卡片都是有时间范围的视图。恢复研究时核对最新状态；如果最新记录不可访问，明确标注“截至上次核实”，不得把旧运行状态重新宣告为当前状态。

## 7. 完整 Draft 示例

下例为虚构的排版与语义示例。假设用户已提供研究目标、梁尺寸和弹性材料资料，而项目、模型与 Subagent 尚未建立。数值只用于说明格式，不是默认研究合同、推荐模型或已完成的工程结果。

实际使用时逐项替换研究内容和状态，保留排版骨架。输出给用户时去掉外层代码围栏。

```markdown
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## ⚛️ CAE Agent · Research Workspace

**Beam-InvOpt（建议名称）**　`Draft 01`　`Planning`

### ❶ Research Contract

> **研究命题**
>
> 反求悬臂梁自由端目标测点达到 **−1.00 mm** 位移所需的静载荷，并研究厚度变化对刚度和应力分布的影响。

**基准模型**：拟采用 100 × 10 × 5 mm 钢制悬臂梁，左端固支；候选模型尚未建立，资格待确认。

**研究交付**：Sanity Model、载荷反求、参数研究、独立验证。

`研究方案草案`　`尚未正式登记`　`尚未执行计算`

### ❷ Research Assumptions

**已提供**：几何尺寸、材料弹性参数、目标位移。

**暂定假设**：线弹性静力分析、端面分布载荷。

**待确认**：项目名称、测点与方向、加载方式、验收标准及厚度范围。

### ❸ Model Evolution

| 模型版本 | 相对基准的变化 | 状态 |
| --- | --- | --- |
| **M0 · Theory** | 拟以 Euler–Bernoulli 梁理论作参考，适用性待检查 | ⚪ 拟议 |
| **M1 · Sanity** | 拟建立 3D 有限元候选基准模型 | 🟡 模型定义待确认 |
| **M2 · Parametric** | 基于取得相应用途资格的 M1 开展厚度扫描 | ⚪ 未开始 |

*以上为模型演进规划；M0 是拟议理论依据，M1、M2 尚未实际建立或验证。*

### ❹ Research Subagent

| 🧠 **Main Agent** | ⚙️ **CAE Subagent** |
| --- | --- |
| 科研规划与决策 | 工程建模与计算输入检查 |
| 🔵 当前对话规划中 | ⚪ 待建立 |

| 📊 **Results Subagent** | 🛡️ **Independent Validation** |
| --- | --- |
| 结果读取与分析 | 独立验证与证据审查 |
| ⚪ 待建立 | ⚪ 按需设置 |

*以上为拟议分工，尚未创建实际 Subagent。Main 表示当前对话的规划职责，尚未完成项目主对话绑定与专业 Subagent 通信验收。*

### ❺ Research Roadmap

- [x] 🟢 **01 · 研究目标理解** — 初步草案已形成
```

## 8. 发布与引用版本

插件内保留已确定的三个工作流 Skill；本文和配套规范在 GitHub 维护，不额外打包为本地引用文件。这一文档分工不改变插件已有的工具连接及运行组件。Skill 应明确要求在生成或更新卡片前读取本规范，而不是仅列出链接后假定内容已被加载。

正式发行版引用经过核对的固定 Git commit。可采用相应 commit 的 `blob/<commit>/...` 人类阅读链接或 `raw/<commit>/...` 内容入口；本文的相对链接随同一 commit 定位配套文档。开发中的 `main` 可用于审阅最新内容，不能静默替换发行版固定的规范版本。

已经读取并核对过的同版本内容可以复用。远端暂时不可访问时，可以使用确认属于相同 commit 的本地副本，或内容摘要已经对照该固定 commit 核对的副本；配套规范同样保持该提交版本。没有可核实的副本时，说明受影响的卡片生成或更新步骤，保留已有资料；不得声称已读取或遵循尚未获得的完整规范。

本规范的发布和 Markdown 检查不等于在所有 Codex 客户端重新完成渲染验收，也不改变既有工具、权限或执行能力。

## 9. 输出前检查

生成完整卡片前核对：

1. 六个模块、标题字符、上下边界和两张双列表格是否完整且顺序正确。
2. 内容是否对应当前项目与本轮任务，草案与正式状态是否区分。
3. Main 是否明确为唯一主对话，专业角色是否按实际创建和通信情况显示。
4. 模型资格、执行进度和研究结论是否分别具有证据，模拟与历史结果是否显著标注。
5. Roadmap 的勾选是否对应已经完成的具体成果。
6. Next Action 是否与实际进度、研究范围和授权一致。
7. 详细模型规格与工程证据是否保存在相应资料中，卡片是否仍然简明可读。
8. 正常工作回复是否位于底部边界之外。
