## 1. 什么是 Sanity Model

在 GD-CAE 中，**Sanity Model 是围绕明确研究问题形成的、能够被检查、解释、逐步完善和演进的工程研究起点。**它让研究者与 Agent 面对同一个具体工程对象，并使后续变化、计算和判断具有可追溯的参照。

它可以最初只包含部分可靠定义：例如几何与材料已经给出，接触、加载时序、输出或验证依据仍需补齐。Agent 应检查现有资料，主动完善有依据的内容，并暴露无法可靠确定的关键事实。随着检查和验证积累，候选模型可以取得指定研究用途的资格，成为后续实验的研究基准。

### 1.1 候选与合格的用语

为避免名称掩盖实际状态，沟通时应带上资格说明：

| 用语 | 含义 | 应说明的内容 |
| --- | --- | --- |
| **Candidate Sanity Model — 候选基准** | 已接收或已建立，定义、适用范围或验证仍待完善 | 已知内容、缺项、拟用途及下一项检查 |
| **Qualified Sanity Model — 合格研究基准** | 对指定用途、范围及判据已有充分的相应证据 | 模型版本、适用范围、证据与限制 |

本指南将 Sanity Model 用于描述上述可演进的模型体系。旧版指南及配套协议中不带限定词、以“已经取得资格”为前提的 **Sanity Model**，对应这里的 **Qualified Sanity Model**。术语扩展不改变现有运行时的状态枚举、准入条件或执行权限，也不将候选自动升级为合格基准。

如果目前只有研究描述和模型定义草案，应注明“模型尚未建立”。一张表格、一个拟议名称或目录不能证明模型文件已经存在。

### 1.2 一个研究起点包含什么

| 内容 | 应回答的问题 | 例子 |
| --- | --- | --- |
| 工程对象与定义 | 研究的是什么，定义在哪里？ | 几何、装配、材料赋值、网格、约束、接触、分析步与输出 |
| 研究用途与变化范围 | 要回答什么问题，什么可以改变？ | 优化扫描顺序；保持约定的材料、热输入规则和支承条件 |
| 已知、假设与缺项 | 哪些有来源，哪些仍需完善？ | 已读取的边界条件、暂定简化、未知单位或缺失数据 |
| 验证依据与范围 | 凭什么支持这项用途？ | 理论对照、实验数据、独立检查、误差判据和未决问题 |

一份 `.cae` 可以提供具体定义，但文件存在、能够打开或曾经算成功，都不足以单独证明研究资格。Sanity Model 也不必是极简演示模型；它需要保留研究结论所依赖的关键物理过程。小型验证算例和项目基准可以并存，分别检验局部机制和整体研究设置。

## 2. 为什么它是正式研究的起点

自然语言适合表达目标、讨论假设和解释决策；复杂几何、区域选择、装配关系及随时间变化的条件，需要具体工程表示承载。Sanity Model 将这些定义组织为能够检查和比较的对象，支持以下工作：

1. **明确研究对象。**能够定位到具体零件、材料、区域、集合和分析步。
2. **建立比较条件。**能够解释候选差异来自哪些计划中的变化。
3. **约束研究变量。**Agent 能在约定范围内主动探索。
4. **保留证据。**能够追查结果来自哪个模型版本、哪些输入及依赖。
5. **识别需要复核的范围。**新的条件或主张超出原有证据时，补充针对性验证。

**Verified-Model-First 的含义是：在使用模型支持正式科研结论之前，先取得与该结论相匹配的模型资格。**

需求澄清、候选建模、静态检查和资格试验可以发生在合格基准确立之前。在已有授权与预算范围内，候选基准可以用于探索或验证计算；记录必须说明其目的和限制。不得将资格要求实现为“没有完成验证计算，就不允许进行验证计算”的循环阻断。

未经相应用途验证的结果可以用于定位问题、形成假设或安排下一轮工作，但不能提前表述为已经接受的正式科研结论。

## 3. 谁来建立基准

GD-CAE 支持以下两种方法入口；具体版本实际提供哪些工具，需要另行核实。

| 入口 | 工作方式 | 取得基准资格的条件 |
| --- | --- | --- |
| 接手已有模型 | 研究者提供模型和资料，Agent 检查定义、依赖及适用范围 | 对当前用途有充分的相应检查和验证证据 |
| Agent 建立模型 | 从研究目标和已有资料提出候选，逐步建模、检查、修订与验证 | 与人工模型采用相同的证据要求 |

人工预制 `.cae` 不是所有任务的强制入口。模型创建者的身份不代替证据；人工模型中的关键未知也应保留。

### 3.1 Agent 如何完善不完整的模型

按以下顺序处理缺项：

1. 检查现有模型、脚本、实验资料、研究合同和已有报告，定位可直接确认的事实。
2. 在允许范围内补齐能够可靠实现的技术定义，记录来源、理由和实际变化。
3. 对合理但尚未证实的建模选择，明确标为假设，并安排适当检查。
4. 对影响物理解释且无法可靠推断的事项，由 Main 向用户提出具体问题；说明缺项影响什么、有哪些可选处理方式。

例如，已经明确的目标测点未被输出请求覆盖，可以在获准范围内补充输出；材料测试数据的来源、真实夹持方式或仪器柔度若没有依据，应保留待确认。不得用看似合理的数值掩盖关键未知。

## 4. 需要区分的四种对象

| 对象 | 含义 | 可以支持的工作 |
| --- | --- | --- |
| 候选模型 | 已建立或接收，定义完善或资格检查尚未完成的 Candidate Sanity Model | 描述定义、诊断问题和开展获准的探索或资格试验 |
| 研究基准 | 对指定任务、范围和判据已有相应证据的 Qualified Sanity Model | 在资格范围内作为正式比较的参照 |
| 实验候选 | 基于明确模型版本，改变本轮约定变量形成的模型或计算输入 | 检验具体方案；结果仍需检查和评价 |
| 基准修订 | 改变原基准重要假设、结构或比较条件的新版本 | 复核受影响资格后，成为后续研究的新参照 |

这些是研究对象的语义说明，不是新增的强制数据库类型或后端状态。实际记录使用当前正式接口支持的对象和标识。

合格基准派生的候选不自动取得所有资格。一次候选失败不一定否定整个基准；一次求解成功也不自动证明候选的科学价值。尚未合格的父模型同样可以产生用于资格试验的候选，但相关限制应随任务和结果保留。

## 5. Agent 可以主动改变什么

改变物理条件本身可以是数值实验的一部分。根据研究目标区分以下三类内容：

| 类别 | 含义 | 处理原则 |
| --- | --- | --- |
| 研究变量 | 本轮主动改变的因素 | 在确认范围内自主设计，保留数值、单位和参数映射 |
| 比较条件 | 为解释差异而保持一致的条件 | 明确记录并检查；变化时说明影响和修订关系 |
| 观测结果 | 数值实验产生的响应 | 按约定的指标、区域、时刻和提取方式分析 |

这些类别取决于任务。同一个摩擦系数可以是材料反演中的比较条件，也可以是接触研究中的研究变量。Step、Interaction、Load、材料或网格的对象类型不决定其是否允许变化；应以本轮研究约定为准。

### 5.1 RL-LAM：扫描顺序研究

对于比较 `[1, 2, 3, 4, …]` 与 `[7, 9, 2, 4, …]` 等顺序的任务，Step 顺序及热区加载时序可以变化。不同温度历程和最终变形正是需要观察的响应。

应检查每个序列位置与物理热区的对应、载荷激活与失活、漏道或重复加热，以及冷却和结果评价条件。热输入规则、支承、路径转换和停留时间中哪些保持一致，需要由研究设计明确。

扫描顺序可能改变真实行程和过程时间；不得为了形式上的“可比较”擅自消除研究本来要观察的影响。若同时探索速度、功率或停留时间，应将其加入变量范围和验证要求。

### 5.2 SP-InvOpt：材料参数反演

对于 `sigma_y` 和 `n` 的反演，应明确本构公式、应力应变定义、单位、拟合区间及材料表生成方式。离散材料表不一定能唯一还原原始参数化公式，应结合实际本构类型和生成依据判断。

几何、厚度、夹持、摩擦和结果提取方式可能影响参数判断。多个参数或假设若能相互补偿，力—位移曲线吻合仍不足以证明材料参数唯一且正确。应使用独立依据约束关键条件，或报告可辨识性与不确定性。

以上为研究方法示例，不声明本次已建立模型、运行实验或完成相应项目验收。

## 6. 修改边界与自主性

### 6.1 保留比较基线，同时允许演进

为一次明确的比较固定父模型版本、研究约定和评价定义，保留源文件及其依赖。候选在可区分的版本或工作位置产生，不覆盖作为既有证据依据的原件。

记录模型身份时，应能够定位源文件、目标 Model / Job、相关依赖、生成或提取工具版本，以及必要的文件摘要。哈希能帮助判断字节是否变化，不能单独证明可信来源、工程语义或物理正确性。

模型修订应说明父版本、修改内容、修改理由、允许范围和受影响的验证证据。原基准及其历史结论继续可追溯；新版本用于哪些后续比较，应明确记录。

### 6.2 自主推进与必要确认

Agent 可以在已经确认的研究约定、资源预算和有效执行权限内连续推进，不需要对每次例行 Step 或 Load 修改重新请求同一授权。

若下一步超出允许变化、改变关键研究前提或需要新的资源与执行权限，应由 Main 说明影响并取得相应确认。确认模型定义或研究合同，不自动授予真实计算权限。

**需要启动 Abaqus 的求解、CAE/noGUI 操作，以及需要 Abaqus 进程的生产后处理，均遵循 AbqJobPilot 的受控执行边界。**读取已有文本或已导出的数据不等于启动 Abaqus；“只是读取 ODB”也不能成为另建启动器的理由。具体边界见 [ADR-003](../adr/ADR-003-codex-native-delegated-execution.md)。当前后端不支持所需操作时，保留候选、缺项和后续建议。

### 6.3 按实际影响复核

以下变化通常需要检查原有证据是否仍适用：

- 物理对象、建模维度、本构、接触或支承理想化发生实质变化。
- 参数、速度、温度或工况超出原验证范围。
- 新的观测量、提取区域、评价时刻或指标改变了研究主张。
- 求解器、重要依赖或执行配置变化，可能影响结果解释。
- 新证据暴露原有模型、测量或参数可辨识性问题。

复核应针对受影响的主张。改变输出频率首先影响观测，改变加载速率可能影响准静态假设，改变夹持可能影响载荷传递；应据此选择检查，不机械地重做所有验证。

探索性候选允许失败。保留失败输入、观察和诊断，并与已接受结果分别记录。

## 7. 基准需要验证到什么程度

资格验证应回答：**现有证据是否足以支持这项指定的研究用途？**

| 检查或验证 | 能提供的证据 | 不能单独证明的内容 |
| --- | --- | --- |
| 文件与对象检查 | 对象可访问、关联明确、依赖已识别 | 物理假设正确 |
| 结构和量纲检查 | 缺项、明显冲突及部分单位问题 | 复杂非线性全过程稳定 |
| 成功完成求解 | 此次输入在此次环境完成计算 | 模型代表真实对象，或结果足够准确 |
| 理论或简化基准对照 | 特定机制、实现或极限情况得到检查 | 所有复杂工况都适用 |
| 网格与时间离散研究 | 特定结果对离散设置的敏感性 | 本构与边界条件符合实际 |
| 实验或独立结果对照 | 指定观测量及适用条件得到检验 | 参数唯一可辨识，或范围外预测可靠 |

不要求所有任务执行同一张验证清单。应在实验前选择与主要风险和研究主张相称的指标、判据和依据；数值阈值来自研究要求与适用依据，不将示例中的容差当作全项目默认值。需要修改判据时，保留原判据、理由和合同修订，不倒改已有实验的接受条件。

### 7.1 一份资格说明至少回答什么

- 对应哪个模型版本、研究用途和观测量。
- 哪些物理假设、参数和工况范围受到支持。
- 进行了哪些检查，采用哪些判据及独立依据。
- 实际证据和验证记录在哪里，哪些重要问题尚未解决。
- 允许得出多强的结论，何种变化会触发复核。

可用文字说明“候选，等待接触验证”“在指定载荷范围内支持位移比较”或“新工况需复核”。这些说明用于传达实际状态，不替代正式接口的资格记录。

### 7.2 独立验证与结论边界

独立验证应有能检验关键主张的依据，例如解析关系、独立实验、不同实现或单独核对的参考答案。两个 Agent 阅读相同资料后给出相同解释，不能自动排除共同错误。

Results Subagent 的数据分析与独立验证分别承担责任；必要时增加 Independent Validation Subagent，其会话身份本身不能证明方法独立。数值健康、目标满足和物理支持应分别报告，参见 [ADR-004](../adr/ADR-004-execution-evidence-research-verification.md)。

Main 或审查 Agent 可以提出科学判断，但其意见、模型定义表和报告不能自行产生 Core 的正式 VerificationRecord 或机器 `PASS`。正式验证状态必须来自当前系统支持的验证流程及实际记录；缺少对应能力时，保留分析意见及未决状态。

Fixture 或 TEST_ONLY 只能说明相应模拟流程的行为，不能赋予真实工程模型物理资格。真实 Solver 计算若使用合成目标，也应说明目标来源；其结果不自动构成实验验证。

## 8. 必须提供 `.cae` 吗

不必须。选择能承载任务所需信息、能够检查来源和变化的表示：

| 表示 | 适合的用途 | 使用边界 |
| --- | --- | --- |
| 原生 `.cae` | 保存和编辑原生模型对象与作业定义 | 需要相应 Abaqus/CAE 访问能力，外部依赖仍须识别 |
| `.inp` 及其依赖 | 表达求解定义，支持受控工况或材料候选 | 不能作为原生 MDB 全部信息的无损归档 |
| 建模脚本及输入数据 | 参数化、重建和追踪模型生成过程 | 脚本存在或可执行不代表模型已验证 |
| `.odb` 及执行证据 | 检查已保存的模型和计算结果信息 | 不能替代原始建模假设与完整依赖 |

对于改变扫描顺序或材料表的任务，生成候选 INP 可以是合理路径。应保留父基准、参数映射、实际输入和比较条件检查；不必仅为形式完整而要求每个候选另存 `.cae`。

需要原生几何或特征编辑时，应采用能保留有关信息的工作路径。Abaqus 手册说明，INP 无法存储 MDB 的全部数据，回读的 Parts 以网格形式导入，未支持的关键字可能被忽略。[R1][R2]

历史 `.jnl`、`.rpy` 等文件可以提供建模线索，但其内容可能包含修改或提交动作。检查内容与执行文件是不同操作，按任务范围分别处理。

## 9. Codex 能理解模型到什么程度

Codex 的文件和工具能力、Abaqus 的对象接口，可以为模型理解提供具体观测；接口机制存在不证明当前插件已经正确实现或执行了它。[R3][R4]

以下分级用于组织证据，不是通用准确率或功能承诺：

| 等级 | 能力 | 使用时应关注什么 |
| --- | --- | --- |
| L0 文件识别 | 确认文件和来源线索 | 是否找到了正确文件与版本 |
| L1 定义读取 | 读取对象和属性 | 是否准确、是否遗漏关键内容 |
| L2 关系重建 | 关联赋值、区域、接触、步状态和输出 | 是否对应目标工程对象及有效时刻 |
| L3 工程解释 | 解释物理角色、假设和研究含义 | 哪些是事实、推断或未知 |
| L4 受控修改 | 生成候选并检查允许变化和比较条件 | 是否保留了可核查的变更证据 |
| L5 科研适用性验证 | 检验指定用途和主张 | 是否有独立依据和明确范围 |

给出复杂 `.cae` 不能直接推定达到 L3 至 L5。没有可用的 Abaqus 工具时，可以分析已有 INP、脚本和报告，但应标注来源；不能将这些资料的解释称为从二进制 `.cae` 完整读取成功。

模型理解等级、模型资格、软件环境可用性、执行授权和研究目标达成是不同判断。每项结论只报告实际完成的范围。

## 10. 如何开始一个任务

已有模型时，优先提供：

- 研究目标与主要评价量。
- 模型位置和希望使用的 Model、Job 或版本；不清楚时可明确说明。
- 已知单位、本构定义、外部子程序及数据。
- 已有验证依据、限制和担忧。
- 希望探索的变量、比较条件和资源预算。

信息不完整时，Agent 先检查可获得事实，再提出具体缺项。研究者无需先用自然语言重述全部模型细节。没有模型时，可以从目标、几何与材料资料、可用验证数据和主要假设开始，由 CAE Subagent 在授权范围内组织候选建模。

在后续使用中，应始终能够回答：当前模型是什么；已经完善到哪里；对什么用途具有依据；本轮允许改变什么；下一项工作为什么有必要。

## 11. Sanity Model Specification — 模型定义表

### 11.1 保存位置与身份

在已确认的项目工作空间中，将当前模型定义摘要保存为 `models/SANITY_MODEL_SPEC.md`。已有项目优先沿用可定位的等价位置，并在 Handoff 与研究记录中注明，不因采用本指南强行搬迁工程文件。

表格前记录：项目身份、当前模型版本及父版本、源文件和依赖位置、实际建立状态、拟用研究问题、资格范围，以及相应证据引用。若已有正式模型或候选标识，引用真实回执中的值；未登记时明确保留草案状态。

文件和表格是可读摘要。真实模型、生成输入、执行产物和正式资格记录保留各自身份，不能以“表格已填满”替代。

### 11.2 模型定义表模板

下表中的说明是填写要求，不是已确认的模型参数。每行按实际任务填写；来源可放在模型定义中或表后引用，复杂内容链接到对应资料。

| 项目 | 模型定义 | 状态 |
| --- | --- | --- |
| Research Objective | 研究问题、目标量、测点和评价方式 | 待确认 |
| Geometry | 几何、尺寸、建模维度及关键简化 | 待检查 |
| Material | 材料、本构、赋值区域及数据来源 | 待检查 |
| Step | 分析类型、步骤、时间或增量设置及有效时序 | 待检查 |
| Boundary Conditions | 支承、约束、自由度、区域及坐标系 | 待检查 |
| Loads | 载荷、施加区域、方向、幅值和时序 | 待检查 |
| Interactions | 接触、相互作用、连接与有关参数 | 待检查 |
| Mesh | 单元类型、网格策略及必要的质量检查 | 待检查 |
| Outputs | 输出变量、区域、坐标、频率和指标提取方式 | 待检查 |
| Units | 使用的单位制及其明确依据 | 待确认 |
| Dependencies | 包含文件、子程序、材料数据和其他必要依赖 | 待检查 |
| Research Variables | 允许改变的变量、范围、参数映射和比较条件 | 待确认 |
| Validation | 验证用途、计划或已有依据、判据与限制 | 待确认 |

保留与当前研究有关的内容。确实不涉及的项目可写“不适用”并解释依据；缺失信息不能以“不适用”代替。

### 11.3 状态与展示

- **已提供：**已有用户或资料输入，注明来源；不自动等于内容已验证。
- **已读取／已核对：**完成了所说明范围的读取或一致性检查。
- **假设：**为当前研究采用、仍需说明依据和适用限制的选择。
- **待检查／待确认：**证据或必要决定尚缺，注明对下一步的影响。
- **不适用：**有理由确认该项不属于当前模型或用途。

以上为可读标记，使用时应匹配实际事实；整模型资格另行说明。需要表示通过验证时，说明具体检查、判据和证据，不只写“已验证”。

首次完成模型理解后展示一次完整表格；模型定义或版本发生变化时重新展示。资格证据和未决事项变化应及时更新保存，并在相关 Research Card 或工作回复中报告；不因每次普通回复重复整张表格。

## 12. 初始化、持续研究与工作交接

| Skill | 与 Sanity Model 相关的责任 |
| --- | --- |
| **Initiate CAE Research** | 记录初步模型定义、实际建立状态、版本线索和资格缺口，随初始化 Handoff 移交 |
| **Conduct CAE Research** | 由 Main 组织完善、资格试验、正式实验、结果分析、独立验证和模型演进 |
| **Set Up Research Environment** | 核实软件、连接和受支持能力；环境安装成功不等于模型取得研究资格 |

初始化允许移交尚待完善的候选，不以全部验证通过作为交接的先决条件。交接时应清楚指出哪些事项仍未完成，不能将待验证模型描述为已合格。

Main 负责研究决策和必要的用户确认；CAE Subagent 负责模型与输入；Results Subagent 负责数据提取与分析。需要时组织独立验证。真实角色创建与通信可用性，按工作流规范核实。

Handoff 引用 `models/SANITY_MODEL_SPEC.md` 及模型证据的位置，Research Card 展示简明模型摘要和演进状态。完整模型定义不重复塞入任务卡。每次有意义的模型工作，在 `docs/research-runs/` 的科研日志中记录变化、证据与下一步。

重开对话时，结合最新正式状态、实际模型与近期记录恢复；旧 Handoff 只是当时的快照。项目身份、模型文件、资格记录或执行证据冲突时，先核对来源，保留未决事实。

## 13. 文档版本与读取要求

需要建立、完善、审查或重新评价 Sanity Model 时，读取本指南及与任务相关的配套规范。正式发行的 Skill 应引用固定 Git 提交，并记录发行版本到该提交的对应关系，使同一发行中的规范保持一致；文档的 `main` 分支用于持续维护。

远端暂时无法读取时，可以使用已经核对为相同提交的本地副本，并记录所采用的版本。没有可核实副本时，应说明缺失的规范；继续不依赖该缺项的讨论或草案，不假装已经读取，也不静默切换为其他版本的执行规则。

本指南不新增工具、数据库字段或执行权限。具体操作还应符合实际任务授权、当前版本接口及其正式回执。更多操作细节见 [工作流与证据规范](../skill-guides/RESEARCH_WORKFLOW_AND_EVIDENCE.md)。
